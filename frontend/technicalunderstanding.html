🚀 Deployment Flow
🚨
NEVER push to staging or main without explicit user (Neelmani) approval.

Every push to staging or main triggers a Render build and auto-deploys to live servers.

  1. Develop on develop branch
    All feature work, bug fixes, and experiments go on develop. Never commit directly to main or staging.
  2. Run pre-deploy check
    bash scripts/pre-deploy-check.sh — also run JWT_SECRET=test_secret python3 -m pytest tests/ -x -q to verify all 1,675+ tests pass.
  3. Run graph review (AI agent only)
    Use detect_changes + get_impact_radius + get_affected_flows from the code-review-graph MCP tools.
  4. Merge develop → staging
    git checkout staging && git merge develop --no-ff -m "release: vX.Y.Z — staging deploy" && git push origin staging
    Wait ~2 min for Render staging deploy.
  5. Verify staging health
    curl https://messenger-crm-staging.onrender.com/api/health/deep
    Must return {"db_tables_accessible": true}. Also test with authenticated API calls.
  6. Update release notes (TWO files, mandatory)
    Add entry to docs/RELEASES.md AND append an entry to frontend-react/src/features/help-hub/data/releases.json (the in-app "What's New" section, since the Help Hub migration — was frontend/js/views/user_guide.js before that). Skipping either = incomplete release.
  7. Merge staging → main
    git checkout main && git merge staging --no-ff -m "release: vX.Y.Z — production deploy" && git push origin main
    Production auto-deploys in ~2 min.
  8. Post-deploy verification
    Check /api/health, /api/health/deep, /api/monitoring/health?key=ls-monitor-v1-2026, Render logs for [Startup] Background tasks complete and [Startup] DB type: postgresql.

🚨 Incident Playbook

P1: App is Down (500 / no response)

  1. Check Render Dashboard
    Open Render → messenger-crm-prod → Events. Look for server_failed, OOM (exit 137), or deploy failures.
  2. Check logs for known patterns
    Look for: [Startup] DB type: postgresql (if sqlite → DATABASE_URL missing), [Startup] DB sanity: N leads where N must be >0.
  3. If env vars suspect
    Run python3 scripts/render_env_manager.py list and compare against scripts/.prod.env line-by-line. NEVER restore from memory.
  4. Rollback if needed
    Render Dashboard → messenger-crm-prod → Manual Deploy → select last known good commit hash. Do NOT git revert a merge.
  5. Fix forward on develop
    Fix the issue on develop, run tests, then get explicit approval before merging to staging → main.

P1 Exception: Skip Staging (only during active outage)

⚠️
When to use the P1 exception path

Only when: (1) there is an active user-impacting outage, AND (2) staging is also affected or unavailable. Fix on develop, test locally, then deploy to main WITH EXPLICIT user approval. Document the staging bypass in the release note. Write an RCA within 24h.

SDR Stuck "Active Call" (Ghost Call)

Symptom: SDR sees "You already have an active call in progress" and can't make new calls.

Self-healing path (v9.5.4+): The frontend auto-detects and clears ghost calls on retry. SDR should see "✅ Cleared a stuck call."

Manual fix: Find the stuck DialerCall record in the DB and set status = 'CALL_ENDED', ended_at = now(). Or wait for the 15-min stale call sweeper (runs every 900s on the backend).

Salesforce Sync Errors

Check Admin → SF Logs in the app for specific error types:

  • INVALID_EMAIL_ADDRESS — Email sanitizer should catch this; check salesforce.py _sanitize_email()
  • DUPLICATES_DETECTED — Gracefully links to existing lead (v8.5.0+); check SF Logs for linked_to_existing_duplicate
  • Resource Lead Not Found — Local ID (MIG-/MANUAL-/upload-) reached SF; check sentinel ID guard in salesforce.py
  • auth_required on connection status — SF credentials expired; re-enter in Admin → Settings → Salesforce

⚠️ Known Issues / Gotchas

Critical Gotchas (Read Before Touching Core Code)

  • 🚨
    DATABASE_URL must NEVER have a SQLite default
    Do NOT add os.getenv("DATABASE_URL", "sqlite:///./crm.db") in database.py. If DATABASE_URL is missing, the app must fail loudly. SQLite fallback = silent 0-leads production incident (RCA 2026-05-13).
  • 🚨
    Lead import: single atomic commit (Rule 11)
    Any route creating leads MUST commit leads AND LeadUploadLog in a single db.commit(). Two separate commits = split-brain risk. Per-row loops MUST use db.begin_nested() savepoints.
  • 🚨
    Column migrations must fail loudly (Rule 12)
    A silent column migration failure lets the ORM boot but all queries fail with ProgrammingError. /api/health (COUNT(*)) still returns 200. Dashboard 500s for users. Always raise, never catch-and-log.
  • 🔑
    Alternate Messenger payload format is exact — no guessing
    Developer curl examples and documentation were wrong. The real contract was discovered from 44 live call records (2026-06-12). Only send: phone_number (E.164), from_number (verbatim from Settings), use_agent_phone, contact_name. Extra fields cause 422.
  • ⚡
    Dashboard OOM: 7 concurrent API calls (fixed in v9.7.7)
    The React Dashboard fired 7 simultaneous API calls on mount. Fixed with 200/400/600/800ms staggering. Also: growth_intelligence_routes.py had an unbounded module-level dict — migrated to cache.py in v9.7.7. Do not reintroduce module-level dicts as caches.
  • ⛔
    Never git revert a merge commit in production
    git revert on a merge commit silently drops ALL changes from that branch. Subsequent merges will NOT re-apply them. Always roll back via Render Manual Deploy → previous commit hash.
